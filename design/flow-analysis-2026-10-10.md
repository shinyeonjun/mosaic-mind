# MK1 처리 흐름 조사 (2026-10-10)

## 1. 시험별 실제 흐름 (코드 기준)

| 시험 | 파일 | 흐름 | 결정 방식 |
|---|---|---|---|
| RGB | `mk1v2/system.py` | E2B 답 + 읽기 위성(문서마다 답·여백) + E2B 짧은 답 → NLI 지지도 → 결정 | 손으로 쓴 규칙, 문턱 2개 (dev 격자 탐색) |
| MuSiQue | `mk1v2/think.py` | E2B 답 + 선택기 사슬 → 다단계 독해기 → 결정 | 손으로 쓴 규칙, 문턱 3개 (dev 격자 탐색) |
| 새 과제 흐름 | `mk1v2/taskstream.py` | E2B 답 + 과제마다 키우는 부품 → 세는 중재자 | **피드백으로 온라인 학습** |
| ARC | `mk1v2/arc.py` | 탐색기 먼저 → 못 찾으면 E2B 답 | 고정 순서 |

공통 모양: **말하기 위성이 기본 답 → 다른 위성이 신호를 냄 → 결정 규칙이 통과/거부/교체.**

## 2. 원래 MK1(가상 세계)과의 차이

`mk1/system.py`에는 칠판(이름 붙은 칸, 쓰기 기록), 배운 라우터(누구에게 물을지), 배운 중재자(누구를 믿을지), 검증 루프가 있었다. MK1 v2에는 **하나도 이어지지 않았다.** v2는 텐서 칠판이 아니라 시험마다 따로 짠 파이썬 함수다.

## 3. 문제점

1. **하나의 시스템이 아니다.** 시험 네 개에 배선 네 개. 어떤 위성을 쓸지는 내가(엔지니어가) 시험을 보고 정했다. 입력을 보고 스스로 도구를 고르는 부분이 없다. "판단"의 가장 기본이 빠져 있다.
2. **결정 규칙이 손으로 쓴 문턱이다.** RGB·MuSiQue는 dev에서 격자 탐색한 고정 문턱이다. 배운 중재자(세는 중재자, 변화 감지 중재자)는 새 과제 흐름에서만 쓴다. 세 시험의 결정 방식이 서로 다르다.
3. **위성끼리 정보가 안 오간다.** 칠판이 없어서 위성은 각자 신호만 내고 서로의 결과를 못 본다. 기록(trace)도 시험마다 제각각이다.
4. **비용 배분이 없다.** 말하기 위성을 항상 부른다. ARC에서는 E2B가 거의 0점인데 시간의 95%를 쓴다. 먼저 싼 위성을 돌리고 필요할 때만 비싼 위성을 부르는 순서가 없다.
5. **흐름이 한 방향이다.** 위성이 거부·교체는 하지만, 더 좋은 맥락을 주고 다시 묻는 고리가 없다. MuSiQue에서 한 번 시도했는데 오히려 나빠졌다(0.36 → 0.22).
6. **배우는 곳이 한 군데다.** 새 과제 흐름만 피드백으로 자란다. 나머지는 dev에서 얼린다.

## 4. 이상적인 흐름 (MK1 v3 제안)

```
입력 → 칠판 (input, kind?, candidates[], evidence[], confidence, cost)
        │
        ├─ 라우터: 입력 모양을 보고 위성을 고른다 (격자 → 탐색기, 문서+질문 → 읽기·선택기, 라벨 흐름 → 키우는 부품)
        │          싼 것부터, 확신이 차면 멈춘다
        ├─ 위성들: 칠판에 후보와 근거를 쓴다 (서로의 후보를 읽을 수 있음)
        ├─ 중재자: 위성 × 입력 종류마다 맞힌 횟수를 세서 저울질 (하나의 규칙, 피드백으로 자람)
        └─ 말하기 위성: 결정된 내용을 말로 낸다 (또는 "모름")
```

판정 방법: **같은 얼린 시스템 하나**가 네 시험 문제가 섞여 들어오는 흐름을 **어느 시험인지 듣지 않고** 푼다. 시험별 v2 점수와 비교해서 덜 떨어지면 통합 성공이다. 이것이 "작은 AGI"에서 "엮었다"를 증명하는 시험이다.
